# Toolbar Implementation Plan

> **For agentic workers:** REQUIRED SUB-SKILL: Use superpowers:subagent-driven-development (recommended) or superpowers:executing-plans to implement this plan task-by-task. Steps use checkbox (`- [ ]`) syntax for tracking.

**Goal:** Phocida shows a Lazarus-style toolbar of icon buttons (New / Open / Save / Save all / Build / Run) as the topmost row of the workspace window; Build runs the default lazbuild task, Run builds then launches the project's exe in the terminal panel.

**Architecture:** A new crate `crates/toolbar` renders the button row and registers its actions, following the `title_bar` slot pattern: a new `set_toolbar_item`/`toolbar_item` slot on `Workspace` rendered above the docks. Build/Run reuse the task pipeline through a new awaited-spawn function in `tasks_ui` (`schedule_resolved_task_with_completion`), and the exe name comes from re-parsing the open `.lpi` with the `lazarus_project` crate.

**Tech Stack:** Rust (toolchain pinned in `rust-toolchain.toml`), GPUI (`ui::IconButton`, `icons::IconName`), existing `task`/`tasks_ui`/`workspace` plumbing.

**Spec:** `docs/superpowers/specs/2026-11-10-toolbar-design.md`

## Global Constraints

- Toolchain: build/run cargo through the pinned toolchain — plain `cargo ...` is enough on this checkout (`rust-toolchain.toml` pins 1.98.1); never pass `--release`.
- License: new crate `toolbar` copies `crates/lazarus_project/Cargo.toml`'s style (`license = "GPL-3.0-or-later"`, `edition.workspace`, `[lints] workspace = true`, `doctest = false`); no new license files.
- Crate members go into root `Cargo.toml` `members` alphabetically; `[workspace.dependencies]` entry `toolbar = { path = "crates/toolbar" }`.
- Toolbar deps are exactly: `gpui`, `ui`, `icons`, `workspace`, `tasks_ui`, `anyhow`, `task`, `lazarus_project`, `smol`, `futures` — no collab/client/languages/project.
- Buttons trigger existing actions only (`workspace::{NewFile, Open, Save, SaveAll}`); toolbar itself never re-implements their logic.
- Icons from the existing `icons` crate only, nearest by meaning: New = `FileGeneric`, Open = `FolderOpen`, Save = `Save` if present else `FileGeneric` (see Task 4: `icons` has no save-like icon; `FileGeneric` is the accepted stand-in), Save all = `FileGeneric` variant via tooltip distinction, Build = `ToolHammer`, Run = `PlayFilled`. No new assets.
- `pascal_task_context` heuristic stays untouched; the `.lpi` provider templates get the `lazbuild` tag added.
- Errors (missing main unit, failed build) surface through `workspace` notifications/toasts, never panic; "no matching task" falls back to the existing task-spawn modal.
- No hardcoded keybindings for the new actions; buttons are the only entry points in this milestone.

## Review Focus

1. `.lpi` templates with a `lazbuild` tag but multiple build modes — Build must pick exactly the one template without `--build-mode`, not the first one blindly. *Pinned by Task 1 test `default_mode_predicate_skips_flagged`.*
2. Run pressed with no open `.lpi` at all — must show a notification naming the problem, not panic, not launch anything. *Pinned by Task 3 test `run_without_lpi_is_an_error`.*
3. Main unit missing from the `.lpi` — exe name falls back to the `.lpi` stem + `.exe`. *Pinned by Task 3 test `exe_name_falls_back_to_lpi_stem`.*
4. Build scheduled with the completion-aware path — a failed build must surface `Failure` to the caller (Run must not launch a stale exe). *Pinned by Task 2 test: `spawn_task_awaited` resolves only after the completion callback fired and passes the result through.*
5. Workspace renders with and without a toolbar item — `toolbar_item: None` must not break the existing layout (single-file workspaces, dock-only windows). *Pinned by Task 4 test `workspace_renders_without_toolbar_item` and by Task 4 verification `cargo build -p zed` + full workspace test compile.*
