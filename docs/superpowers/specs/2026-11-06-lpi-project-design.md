# Веха 1 — «Проект как главный»: нативный минимальный разбор `.lpi`

Дата: 2026-11-06 · Ветка: `phocida`

## Зачем

Phocida — узкая IDE для Free Pascal/Lazarus (форк Zed). Цель — открыть папку Lazarus-проекта
и работать (сборка, отладка, агенты) без ручной настройки. Сейчас редактор «видит» проект
только по эвристике: шаблон задачи lazbuild строится как `{dir}/{stem}.lpi` рядом с `.lpr`,
а атрибуты проекта (title, build modes) не читаются вовсе.

После вехи: открытый `.lpi` даёт честные задачи сборки — по названию проекта и по каждому
build mode, без догадок об имени.

## Подходы, о которых мы говорили

1. **Полный нативный парсер** (проект, юниты, пути, пакетные зависимости, project panel) —
   отложен: слишком тяжело рано, а закрывает больше цикла сборки, чем редактору нужно сейчас.
2. **Чисто языковой путь** (`tree-sitter-lpi`) — уже сделан на ветке: `.lpi`/`.lpk`
   подсвечиваются, есть outline и скобки. Но это только редактирование текста — «IDE» не даёт.
3. **Гибрид (выбран): минимальный нативный разбор `.lpi` ради цикла сборки**, остальное
   продолжает жить в текстовом редакторе.

## Решение

### Объём парсера (минимум, чего требует цикл сборки)

Новый крейт `crates/lazarus_project` с собственной `quick-xml`-разборкой `.lpi`
(зависимость `quick-xml = "0.41"` уже есть в workspace):

- различать `.lpi`-проект от `.lpk`-пакета по наличию `CONFIG/ProjectOptions` либо
  `CONFIG/PackageOptions`;
- для проекта читать:
  - `General/Title` → название проекта (для подписи задач);
  - `General/MainUnit` → индекс главного юнита; по нему его `Units/UnitN/Filename`
    (`.lpr`), из которого берётся стабильное имя проекта при отсутствии `Title`;
  - `BuildModes/Item1..ItemN/Name` → список build modes; без `BuildModes` — один режим
    «Default», без флага при сборке.

Из `.lpk` пока ничего не извлекается (это отдельный шаг вехи про пакеты).

Определённо не сейчас (см. Non-goals): `CompilerOptions/SearchPaths` и их передача в `pasls`
(это веха «пути для LSP на автопилоте»), список юнитов для project panel, реакция на
изменение `.lpi` на диске (сначала достаточно перечитывать текст открытого буфера).

### Задачи

В `crates/languages` появляется `lpi.rs` с контекст-провайдером, привязанным к языку `lpi`
(сейчас у него `context: None`, `adapters: vec![]`). Провайдер читает текст открытого буфера
`.lpi`, разбирает его и выдаёт шаблоны задач:

- по одному на build mode: `lazbuild [--build-mode=<mode>] <путь от корня worktree>`;
- режим по умолчанию идёт без флага и первым в списке;
- подпись — из прецедента `pascal_task_context`: `build project '<title>' with lazbuild`,
  для не-дефолтного режима — `build project '<title>' with lazbuild (<mode>)`;
- при отсутствии `Title` — имя по главному юниту без расширения (`project1.lpr` → `project1`).

Провайдер динамический — по типу `TypeScriptContextProvider::associated_tasks` в
`crates/languages/src/typescript.rs`, получает текст буфера через `Entity<Buffer>`.

Эвристику в `pascal_task_context` (задачу lazbuild рядом с `.lpr`) не трогаем — она остаётся
подсказкой у буфера `.lpr`, а честные задачи живут у буфера `.lpi`.

## Non-goals

- Дизайнер форм; редактор `.lpk` и build modes; правка опций сборки; раздельные пути для
  pasls из `.lpi`; project panel с деревом юнитов; наблюдение за `.lpi` на диске.

## Проверяемость

- Тесты парсера на реальном фикс­туре-тексте `.lpi` (шаблон Lazarus: title, 2 modes,
  ProjectType, Units c IsPartOfProject) и на `.lpk`-фрагменте.
- Тест генерации шаблонов задач: подписи и args — точные значения.
- `cargo test -p lazarus_project -p languages` зелёный; сборка `cargo build -p zed`
  не регрессирует.
